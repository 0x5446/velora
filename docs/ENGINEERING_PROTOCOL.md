# 工程协议

状态：2026-11-16 起生效。适用于 Velora 的推测式重生成重构，以及其后每个 milestone。产品行为契约仍以 [`PRODUCT_TECH_DESIGN.md`](PRODUCT_TECH_DESIGN.md) 为准，直到某个已通过关卡的变更明确修订它。

## 1. 证据等级

写进文档或 PR 的每项结论必须属于下面一类，并附位置：

| 等级 | 含义 | 可以做什么 |
|---|---|---|
| 源码事实 | 当前 git 树里读得到的代码、脚本、配置 | 描述现状 |
| 论文主张 | `speculative-dictation` 的 `paper/main.tex` 与其 `\input` 的 `paper/tables/numbers.tex` | 说明研究结论及其适用条件 |
| 已有实测 | 有命令、硬件、模型版本、样本量、原始或汇总产物路径的测量 | 作为当时条件下的证据 |
| 工程假设 | 尚未在目标产品路径上测量的推断 | 只能写成待验证问题 |
| blocked / TBD | 缺资产、缺权限、缺运行环境，或门槛尚未事前登记 | 不得写成通过 |

论文数字不是产品指标。历史调优报告里的毫秒数不是本 HEAD 的回归结果。设计稿里的百分比不是验收门槛。`LatencyBudgetTests` 比较的是源码常数，不是一次运行的分布。

## 2. 关卡

- 每个 milestone 的通过条件写在 [`MILESTONE_GATES.md`](MILESTONE_GATES.md)。条件必须能由另一个人执行并得到失败。
- 没有证据目录里的产物，就不得把该关卡标为通过。
- 数值门槛必须在看候选结果之前登记。基线还不存在时，门槛保持 TBD，不借用论文或设计稿的数字填上。
- 上一关未通过，不开始下一关的产品改动。产品改动指 `Apps/`、`Velora/Sources/` 和默认模型、提示词、上屏路径。验收设施可以在产品关被阻塞时落地，但它的通过只表示设施自己的测试通过。CPU mock 通过不是 MLX 逐 token 一致，也不是产品 T4。
- 产品 T4、真实 ASR 端到端和 M1 的延迟测量是后面关卡的条件。它们没有测到，不能反过来把已经写完的 M0 审计再打开。
- 文档勘误可以单独提交，但不能夹带行为改动。
- 不把“方案先进”或用户选定方向写成质量通过。调整关卡要写明证据；不得在看到结果后放宽已经登记的质量阈值。缺少对照时标 not judged，不另设一个更低的绝对分数。
- 同一提交只包含一个 milestone 的产品行为变化。协议、devlog、handoff 跟随该提交更新。

## 3. 文档与代码

- 改行为时，同一提交更新 [`DEVLOG.md`](DEVLOG.md) 和 [`HANDOFF.md`](HANDOFF.md)。
- 代码注释、README、设计文档里的命令、模型名、默认值必须与源码一致。发现旧文档过期时，在 devlog 记录，并在下一次触及该行为时修正；不要为了“对齐”大段重写历史报告。
- 不把用户听写原文、journal、受限语料或密钥写进公开仓库。评测只入库命令、哈希、聚合指标和失败类别。
- 不在文档里把未运行的测试写成已通过。

## 4. 证据放哪里

未来实测写入 `docs/evidence/<milestone-id>/`，至少包含：

- `report.md`：硬件、操作系统、软件版本、模型与数据哈希、命令、样本量、指标、结论、未完成项
- 聚合结果（JSON 或表格）
- 指向原始日志的本机路径；原始音频和权重不入库

F0、F1 和 Mac 摘要已经有 `docs/evidence/` 产物。M0 还没有 `docs/evidence/m0/report.md`。没有那份产物，M0 就不能标通过。

## 5. 交接

[`HANDOFF.md`](HANDOFF.md) 始终描述：当前 HEAD、已通过和未通过的关卡、阻塞、下一步的只读或可执行命令、不能做的事。新工程师应只靠仓库文档接手，不依赖聊天记录。
